## The task

From the briefing:

- **Goal:** give every test image exactly one label from a fixed category list.
- **Robustness:** handle variation in size, colour, angle, lighting and background.
- **Hidden test set:** test images are only revealed for the final run, so nothing can be tuned on them.
- **Documentation:** describe the approach, including what was tried and didn't work.
- **Deliverables:**
  1. predictions for every test image, one row per image: `filename, predicted category`
  2. a 1–2 page report: method, accuracy, and the three most common failure cases
  3. a 5-minute presentation
- **Evaluation:** accuracy on the hidden test set, and handling of tricky cases (angles, lighting, similar classes).

This team is responsible only for the 10 natural-object classes below; the 10 man-made classes belong to another team.

## Setup

Developed and tested with **Python 3.14.7** on Windows 11. Python 3.11 or newer (64-bit) works too: the code uses
nothing newer than 3.12 syntax, and PyTorch publishes CUDA builds for 3.11–3.15.

```bash
python -m venv .venv
```

PowerShell: `.\.venv\Scripts\Activate.ps1`. Git Bash: `source .venv/Scripts/activate`.

**Machine with an NVIDIA GPU:** install the CUDA build of PyTorch *before* `requirements.txt`. The plain
`pip install torch` gives a CPU-only build on Windows.

1. Check the Python is 64-bit and a supported version (3.11–3.15 for torch 2.15; 3.10–3.14 for 2.14):

   ```bash
   python -c "import sys, struct; print(sys.version, struct.calcsize('P') * 8, 'bit')"
   ```

2. Check the highest CUDA version your NVIDIA driver supports: the `CUDA Version` (newer drivers label it
   `CUDA UMD Version`) at the top right of

   ```bash
   nvidia-smi
   ```

3. Install from the newest index that is **not higher** than that number:

   | `nvidia-smi` CUDA Version | Index | Gets |
   |---|---|---|
   | 13.2 or newer | `cu132` | torch 2.15.0 + torchvision 0.29.1 |
   | 13.0 – 13.1 | `cu130` | torch 2.14.1 + torchvision 0.29.1 |
   | 12.6 – 12.9, or a GTX 10-series / older card | `cu126` | torch 2.14.1 + torchvision 0.29.1 |
   | below 12.6 | update the NVIDIA driver first | |

   For example, for `cu132`:

   ```bash
   pip install torch torchvision --index-url https://download.pytorch.org/whl/cu132
   ```

   Don't pin `torchvision==0.29.2`: that version exists only as a CPU build, so pinning it gives
   *"No matching distribution found"* on the CUDA indexes. The current list of builds is at
   https://pytorch.org/get-started/locally/.

4. Confirm the GPU is visible:

   ```bash
   python -c "import torch; print(torch.__version__, torch.cuda.is_available(), torch.cuda.get_device_name(0) if torch.cuda.is_available() else '')"
   ```

Then, on every machine:

```bash
pip install -r requirements.txt
```

`requirements.txt` lists minimum versions only, so it keeps an already-installed CUDA build of torch and also
works on other Python versions. On Colab and Kaggle nothing needs installing (see [Colab and Kaggle](#colab-and-kaggle)).

The `.venv` on the original development laptop has the **CPU-only** PyTorch build (`2.15.0+cpu`), because that
machine has no NVIDIA GPU. A CPU build never uses a GPU, even if one is present.

### Where pretrained weights are stored

The first time a notebook builds a model, timm downloads its ImageNet weights from Hugging Face. They are cached
in `C:\Users\<you>\.cache\huggingface\hub\models--timm--<arch>\` and reused afterwards, so later runs work offline.
To keep the cache on another drive, set `HF_HOME` (e.g. `setx HF_HOME D:\hf_cache`) and restart Jupyter.
Approximate sizes: mobilenetv3_large 22 MB, efficientnet_b0 21 MB, vit_small 88 MB, resnet50 100 MB,
convnext_tiny 110 MB.

## Training a model

1. Start Jupyter from the project folder (`jupyter lab`), or open the notebook in VS Code and select the
   `.venv` interpreter as the kernel.
2. Open a notebook in `notebooks/`, adjust the settings cell if needed, and **Run All**.
3. Results appear in `output/<MODEL_NAME>/<timestamp>/`.

Notebook sections:

| Section | What it does |
|---|---|
| Settings | all knobs for this model (table below) |
| Setup | finds the project root (on Colab/Kaggle: clones it from GitHub), finds the data, imports `imgcls`, picks the device and prints which one |
| Model | downloads the pretrained weights (first time only; nothing with `PRETRAINED = False`) and adds a 10-class head |
| Data | discovers classes, builds train/val/test splits and loaders, prints counts per class |
| Train | one line per epoch; saves `best.pth` whenever validation accuracy improves |
| Evaluate | scores `best.pth` once on the test split; shows the confusion matrix and the worst mistakes |
| Predict | writes `predictions.csv` for a folder of new images (the hidden test set) |

Starter notebooks:

| Notebook | timm architecture | LR | Notes |
|---|---|---|---|
| `mobilenetv3_large` | `mobilenetv3_large_100.ra_in1k` | 1e-3 | smallest and fastest; a good first run on CPU |
| `efficientnet_b0` | `efficientnet_b0.ra_in1k` | 1e-3 | light CNN, strong accuracy for its size |
| `resnet50` | `resnet50.a1_in1k` | 5e-4 | classic CNN baseline |
| `convnext_tiny` | `convnext_tiny.fb_in22k_ft_in1k` | 2e-4 | modern CNN pretrained on ImageNet-22k |
| `vit_small` | `vit_small_patch16_224.augreg_in21k_ft_in1k` | 1e-4 | vision transformer; keep `IMG_SIZE = 224` |

| `resnet18_scratch` | `resnet18` | 1e-3 | **trained from scratch**, the stronger attempt: ResNet-18 (easier to train from random weights), 150 epochs, `BATCH_SIZE = 64`, `GRAD_CLIP = 1.0`. About 80 min on a Kaggle T4 if epochs take ~32 s as in the MobileNetV3 run |

### Settings reference

| Setting | Default | Meaning |
|---|---|---|
| `MODEL_NAME` | notebook name | output folder name: `output/<MODEL_NAME>/<timestamp>/` |
| `ARCH` | preset | any timm model name |
| `PRETRAINED` | `True` | start from ImageNet weights |
| `DEVICE` | `"auto"` | `"auto"`: NVIDIA GPU, then Apple GPU, then CPU. `"cuda"`/`"cpu"` force one; asking for a missing GPU falls back to CPU with a warning |
| `IMG_SIZE` | `224` | input resolution |
| `EPOCHS` | `10` | maximum epochs |
| `BATCH_SIZE` | `32` | lower it if the GPU runs out of memory |
| `LR` | preset | peak learning rate (AdamW) |
| `WEIGHT_DECAY` | `0.05` | AdamW weight decay |
| `LABEL_SMOOTHING` | `0.1` | cross-entropy label smoothing |
| `GRAD_CLIP` | `None` | maximum gradient norm, e.g. `1.0`. Caps the size of each update, which prevents the sudden collapses seen when training from scratch. `None` = off (missing in older notebooks, which means off) |
| `TRAIN_MODE` | `"finetune"` | `"finetune"` trains every layer; `"linear_probe"` freezes the backbone and trains only the classifier (much faster on CPU, usually a little less accurate) |
| `VAL_FRACTION` | `0.10` | share of each class's train images held out to choose the best epoch |
| `SAMPLES_PER_CLASS` | `600` | images drawn per class per epoch (class-balanced, with replacement); `None` = every train image once, unbalanced |
| `PATIENCE` | `None` | stop after this many epochs without validation improvement |
| `LIMIT_PER_CLASS` | `None` | use only N images per class (quick smoke tests) |
| `NUM_WORKERS` | `4` | image-loading processes for training, lowered automatically to the number of CPU cores (Colab has 2, Kaggle 4). On Windows, with the CUDA build of PyTorch, use `2` (or `0` if workers hang). Validation/test never use extra processes on Windows |
| `SEED` | `42` | seed for the splits, sampling and initialisation |

### What happens during training

- **Device:** GPU first, then CPU (`imgcls/device.py`). On a GPU, mixed precision (float16) and cuDNN autotuning
  are switched on automatically.
- **Validation split:** `VAL_FRACTION` of each class's train images (stratified, fixed seed) is held out. The best
  epoch is picked on validation accuracy, so **`test/` is used exactly once, after training**. Choosing epochs on the
  test split would make the test accuracy optimistic.
- **Class balance:** a weighted sampler draws `SAMPLES_PER_CLASS` images per class per epoch, so butterfly
  doesn't dominate. An epoch is therefore `10 x 600 = 6,000` samples by default.
- **Augmentation** (train only), aimed at the briefing's size/colour/angle/lighting/background requirement:
  `RandomResizedCrop(scale 0.35–1)`, horizontal flip, `TrivialAugmentWide` (rotation, shear, brightness,
  contrast, colour, sharpness, posterize, solarize, ...), `RandomErasing(p=0.25)`.
  Evaluation: resize to `IMG_SIZE / 0.875`, centre crop.
- **Images:** EXIF rotation applied; transparency flattened onto white; unreadable files are replaced by a grey
  image with a warning instead of crashing.
- **Optimisation:** AdamW, 1 warm-up epoch (when `EPOCHS > 2`), then cosine decay to zero; cross-entropy with label smoothing.
- **Image-loading workers:** on Windows each worker is a separate process that loads all of PyTorch (several GB
  of DLLs for the CUDA build). Starting several pools at once can exhaust memory and hang (`WinError 1455`,
  "paging file is too small"). So on Windows only the training loader uses `NUM_WORKERS` processes, kept alive
  across epochs; validation and test load images in the notebook's own process. The train cell prints when workers
  start and how long they took. If they don't deliver a batch within `LOADER_TIMEOUT` seconds (default 180; add
  `LOADER_TIMEOUT = 300` to the settings cell to change it) or crash, training prints a warning, switches that
  loader to single-process loading and redoes the phase instead of hanging.
- **Checkpointing:** `best.pth` is overwritten whenever validation accuracy improves. **Interrupting the train cell**
  stops training early but keeps `best.pth` and the history.

## Adding a new model

`scripts/create_notebook.py` is the base script that generates notebooks. It never overwrites an existing
notebook unless you pass `--force`.

```bash
python scripts/create_notebook.py --list
```

```bash
python scripts/create_notebook.py --presets
```

```bash
python scripts/create_notebook.py swin_tiny --arch swin_tiny_patch4_window7_224.ms_in1k --lr 1e-4
```

```bash
python scripts/create_notebook.py convnext_tiny_lp --arch convnext_tiny.fb_in22k_ft_in1k --set TRAIN_MODE=linear_probe --set EPOCHS=15
```

- `--arch` takes any timm model name. To browse:
  `python -c "import timm; print(timm.list_models('*efficientnet*', pretrained=True))"`.
  Unknown names are rejected.
- `--set KEY=VALUE` overrides any setting in the generated notebook (repeatable).
- `--lr`, `--epochs`, `--batch-size`, `--img-size` are shortcuts for the common ones.
- To make a model a permanent preset, add it to `PRESETS` in `scripts/create_notebook.py`.
- To change what *every* notebook does, edit `imgcls/` (picked up immediately) rather than the notebooks. Changing
  the notebook template itself only affects notebooks generated afterwards (regenerate with `--force`, which
  discards manual edits).

## Prediction API

`api/main.py` serves a model over HTTP with a single endpoint, **`POST /predict`**: upload an image, get its
category. The model is loaded once at startup.

### Configure

Copy `api/.env.example` to `api/.env` and edit it (`api/.env` is git-ignored):

| Variable | Default | Meaning |
|---|---|---|
| `IMGCLS_CHECKPOINT` | empty | a `best.pth` from `output/<model>/<timestamp>/` (absolute, or relative to the project root). Set: the fine-tuned model predicts our 10 categories. Empty: `IMGCLS_MODEL` is used without training: zero-shot for a CLIP backbone, otherwise its ImageNet classifier (see below) |
| `IMGCLS_MODEL` | `mobilenetv3_large_100.ra_in1k` | timm architecture, used when there is no checkpoint. With a checkpoint it can stay empty; if set, it must match the checkpoint's architecture or the API refuses to start. Without a checkpoint it must be either a CLIP backbone listed in `OPEN_CLIP_NAMES` in `imgcls/zeroshot.py` (runs zero-shot) or a model with an ImageNet classifier (e.g. a `_in1k` tag); anything else is refused before downloading |
| `IMGCLS_DEVICE` | `auto` | `auto` (GPU if available, otherwise CPU), `cuda` or `cpu` |
| `IMGCLS_TOP_K` | `3` | number of guesses in `top_k` |

Example `api/.env` for a fine-tuned model:

```
IMGCLS_CHECKPOINT=output/convnext_tiny/2026-11-20_10-15-00/best.pth
IMGCLS_MODEL=
IMGCLS_DEVICE=auto
IMGCLS_TOP_K=3
```

Example for CLIP with no checkpoint (zero-shot, no training):

```
IMGCLS_CHECKPOINT=
IMGCLS_MODEL=vit_base_patch32_clip_224.datacompxl
```

### Run

From the project root:

```bash
uvicorn api.main:app --env-file api/.env
```

Then open **http://127.0.0.1:8000/** for the web page (good for the presentation demo), or
http://127.0.0.1:8000/docs for the interactive API docs, or call it directly:

```bash
curl -F "file=@data/pug/test/n02110958_10193.jpg" http://127.0.0.1:8000/predict
```

Add `--host 0.0.0.0` to reach it from other machines on the network. Environment variables set in the shell
work too, without `--env-file`.

### Web page

`api/static/index.html` is served at `/` by the same app. Choose images, drop them on the page or paste one
(Ctrl+V); several at once is fine. Each image is sent to `POST /predict` in turn and gets a card with its
preview, the predicted category and confidence, and bars for the top guesses. The line above the results shows
which model answered (fine-tuned checkpoint, zero-shot CLIP or pretrained ImageNet). Errors from the API (unreadable file, too
large) appear on the card. The page has no external dependencies, so it works offline. Open it through the API,
not by double-clicking the file: the browser blocks a `file://` page from calling the API. The page is not
listed in `/docs`, which still shows only `/predict`.

```json
}
```

- **Fine-tuned mode:** `label` and `category` are always one of the 10 categories.
- **Zero-shot CLIP mode** (no checkpoint, `IMGCLS_MODEL` a CLIP backbone): `label` and `category` are always
  one of the 10 categories, like fine-tuned mode, with no training. `imgcls/zeroshot.py` compares the image with
  three prompts per category ("a photo of a pug.", "a close-up photo of a pug.", "a blurry photo of a pug.") and
  softmaxes the similarities. The weights come from `open_clip` (image and text towers, about 0.6 GB for ViT-B-32,
  downloaded to the Hugging Face cache on first use; the DataComp.XL one is the model data screening already used).
  Measured once, not tuned: 30/30 on 3 test photos per class; on the OWLv2 boxes of the 50-photo comparison it
  agreed with the detector on 135 of 143 (fine-tuned MobileNetV3: 85, CLIP linear probe: 131).
- **Pretrained mode** (no checkpoint, an ImageNet model): `label` is the ImageNet class (e.g. `"cabbage butterfly"`, `"daisy"`), and
  `category` is filled only when that ImageNet class corresponds to one of ours: the 4 dog breeds (ImageNet's
  "Eskimo dog" counts as Siberian husky), 6 butterfly species, banana, orange and 7 kinds of mushroom/fungus.
  **ImageNet-1k has no sunflower or pine cone class**, so those come back with `category: null` (a sunflower is
  usually called `"daisy"`). Models with ImageNet-21k/22k heads do know sunflowers.
- Errors: `400` for an empty or unreadable upload, `413` above 20 MB, `422` when no `file` field is sent.

### Video detection: `POST /detect-video`

Finds **every** object of our categories in a video: which ones appear, **when** (time ranges), **where** (a box
per object per analysed frame) and **how many** at once. Objects of other kinds are ignored. Try it in the
**Video** tab of the web page: the boxes are drawn over the playing video, with a clickable timeline per category;
a dashed box means the detector would have named it differently from our model.

It splits the job between two models: a **ready-made detector** (not one we trained) finds **where** objects of our
categories are, and **our fine-tuned classifier names each one**. The classifier alone can't do it: it gives one
answer per picture, so it can't list several objects or say where they are. How it works:

1. Take `fps` frames per second from the video (OpenCV; mp4, mov, avi, webm, ...).
2. Ask **OWLv2** (an open-vocabulary detector: it finds objects described in words) for our categories:
   "a dog", "a banana", "an orange fruit", "a mushroom", "a butterfly", "a sunflower", "a pine cone", ...
   It also gets look-alikes ("a lemon", "a moth", "a daisy", "a cat", "a person", "an acorn"); a box that
   matches a look-alike better than our words is dropped. Phrasings are in `QUERIES` / `DISTRACTORS` in
   `imgcls/detect.py`.
3. Keep boxes scoring at least the threshold (0.30 for OWLv2), one box per object.
4. **Our fine-tuned classifier names every box** (the `/predict` model from `IMGCLS_CHECKPOINT`). Each box is
   cut out with a 5% margin and padded to a square with grey, so a long banana isn't cut off by the
   classifier's centre crop and neighbouring objects stay out of the crop. (An earlier version grew the box
   into a square of the frame instead; a butterfly sitting on a wide, flat cut orange then filled most of the
   orange's crop, and the orange was named "Butterfly".) All boxes of a frame are classified in one batch. The detector's own label
   stays in the answer as `detector_label`, and `agrees` says whether the two models match (any breed matches
   the detector's "Dog"). The final `category` is always our model's.
   Zero-shot CLIP (no checkpoint) also names every box the same way. With a plain ImageNet model (pretrained
   mode) sunflowers and pine cones can't be named, so the detector's labels are used and the ImageNet model only names dog breeds (`Dog (breed unclear)` below 50%).
5. Join neighbouring frames into time ranges per category.

Request (multipart form): `file` (the video, up to 200 MB), optional `fps` (frames analysed per second of video,
default 1, 0.1–10) and `threshold` (minimum box score; default from the detector). At most 300 frames are analysed
per request (`truncated: true` when the video is longer). The detector is loaded on the first video request and
downloaded the first time (about 0.6 GB, to `model_cache/` in the project, git-ignored; `IMGCLS_DETECTOR_CACHE`
changes the folder). Settings: `IMGCLS_DETECTOR`, `IMGCLS_DETECT_THRESHOLD` (see `api/.env.example`).

```bash
curl -F "file=@clip.mp4" -F "fps=1" http://127.0.0.1:8000/detect-video
```

#### Why OWLv2, and the alternatives

Measured on 60 photos from `train/` (6 per class; `test/` was not used to choose anything), CPU, 4 threads:

| Detector | Right category found (threshold) | Box of a wrong category | Oranges / pine cones found | Seconds per frame (this laptop's CPU) |
|---|---|---|---|---|
| **OWLv2** base/16 (chosen) | **93%** (0.30) | 5% | 5 of 6 / 4 of 6 | 10.6 |
| OWL-ViT base/32 | 75% (0.20) | 3% | **0 of 6 / 0 of 6** | 1.4 |

OWL-ViT is 7× faster but missed every orange and every pine cone, so it can't answer "is it in the video". Some
"wrong category" boxes were right: one banana photo also contains a real orange. On a GPU OWLv2 takes a fraction
of a second per frame, so the CPU speed matters only on this laptop: analyse fewer frames (`fps` 0.5–1) here.

Other options considered (not measured):

| Alternative | Why not now |
|---|---|
| Grounding DINO (tiny) | Also finds objects from words and is strong, but slower on CPU and joins all queries into one sentence, which makes look-alike filtering and mapping labels back to our categories messier |
| OmDet-Turbo, MM-Grounding-DINO, LLMDet | Newer open-vocabulary detectors in `transformers`; worth a comparison later, larger downloads |
| YOLO trained on COCO (Ultralytics) | Fast, but COCO only has dog, banana and orange (no butterfly, mushroom, sunflower, pine cone); AGPL-3.0 licence |
| YOLO-World (Ultralytics) | Fast open-vocabulary YOLO; AGPL-3.0 and an extra framework |
| Our own detector | Best long-term (trained on our classes), but needs boxes on thousands of images: about 6,200 of ours have published boxes (Open Images banana/orange/mushroom, Stanford and Tsinghua Dogs), the rest would need auto-labelling and checking |
| Classifier on tiles of each frame | No new model, but no proper boxes and it can't separate overlapping objects |

#### Who names the boxes better: the detector or our model?

Measured on 50 photos from `test/` (5 per class). `test/` is right here: the classifier was trained on `train/`,
so train photos would flatter it, and no setting was chosen from these numbers. The detector found no box in 5
photos (a butterfly, 2 mushrooms, an orange, a pine cone); for the other 45, the strongest box:

| Who names the main box | Right |
|---|---|
| Detector (OWLv2); a dog only needs to be "Dog" | 42 / 45 (93%) |
| Our model; any breed counts as "Dog" | 43 / 45 (96%) |
| Our model; the breed must be right | 40 / 45 (89%) |
| Our model on the whole photo (as `/predict` does) | 49 / 50 (98%) |

Looking at every box where the two disagree (58 of 143 boxes):

- **Our model wins on clear, single objects**: a stinkhorn-type mushroom the detector called "Banana", a banana
  held in front of a dog that the detector called "Dog", a pine cone the detector called "Banana". It also names
  the breed of every dog (5 of 5 pugs), which the detector can't.
- **The detector wins on small crops from cluttered scenes**: 50 of the 58 disagreeing boxes came from just 3
  photos (a heap of grey pine cones, banana slices on toast), and our model said "Butterfly" for 48 of them.
  Disagreeing boxes are small (median about 60 × 60 pixels, against about 200 × 200 for boxes where both agree).
- Why: our classifier learned from whole photos where one object fills the frame. A small, blurry crop of a
  texture is something it never saw, and it must pick one of its 10 classes anyway: it can't say "not sure".
  This is a domain shift, and the main argument for training our own detector, which learns from boxes of every
  size.

#### Update: CLIP classifiers and a tighter crop

Measured again with two CLIP classifiers, the linear probe trained on Kaggle (`output/clip_b32_probe/`) and
zero-shot CLIP (no checkpoint), and with the box crop changed from a square cut of the frame to the box plus 5%
padded to a square. Boxes where the classifier agrees with OWLv2 (any breed counts as "Dog"):

| Classifier | 50 test photos, 143 boxes (old crop) | 50 train photos, 206 boxes: old → new crop | AI-generated butterfly-on-orange video, 64 boxes: old → new crop |
|---|---|---|---|
| MobileNetV3, fine-tuned | 85 | 150 → 152 | 32 → 43 |
| CLIP linear probe | 131 | 169 → 164 | 29 → 49 |
| Zero-shot CLIP | 135 | 190 → 189 | 36 → 57 |

- CLIP names small and odd crops far better than MobileNetV3, and zero-shot CLIP, which never saw our photos, is
  the best box namer. (The two trained models saw the train photos, which flatters both crops alike.)
- The crop hardly matters on ordinary photos but decides scenes where objects touch: with the square crop, the
  butterfly sitting on a wide, flat cut orange filled the orange's crop and every model said "Butterfly".
  The crop was chosen on that video and on train photos, not on `test/`.
- Zero-shot CLIP's 7 remaining misses on the video are thin slivers of the cut orange's edge and one blurry
  background orange (5 called "Golden retriever"), all with confidence 0.66 or less.

#### Limitations

- Our model names every box, including small crops where it is often wrong (see above); the dashed boxes on the
  web page show where the detector disagrees.
- Slow on CPU (about 10 s per analysed frame here); a 1-minute video at 1 frame per second takes about 10 minutes.
- Only the detector decides whether a box is "one of ours"; our classifier always picks one of its 10 classes, so
  it can rename a box but never reject it. A beagle found as "a dog" is named as one of our 4 breeds.
- Each frame is analysed separately: `max_count` is "the most boxes in one frame", not the number of different
  objects in the whole video (that would need tracking).
- Thresholds were chosen on 60 photos and checked on one generated test video, not on real labelled videos.

## Object detection: training our own detector

The video API uses a ready-made detector (OWLv2). `object_detection_notebooks/` trains our own, in three
notebooks generated by `scripts/create_detection_notebooks.py` (shared code in `imgcls/objdet/`). They run
unchanged on this laptop (CPU), the GPU laptop and Kaggle.

| Notebook | What it does | Output |
|---|---|---|
| `01_build_data_object` | gives our photos boxes and writes a detection dataset | `data_object/` |
| `02_yolo` | fine-tunes an Ultralytics YOLO model (`yolo26n.pt`, pretrained on COCO) | `output/yolo26n/<timestamp>/` |
| `03_mobilenet_frcnn` | Faster R-CNN whose backbone is **our own fine-tuned MobileNetV3** (`best.pth`) | `output/frcnn_mobilenetv3/<timestamp>/` |

### Why a separate dataset

A detector learns from boxes; our photos only have a class each. Notebook 01 gives them boxes from two sources:

- **Human boxes from Open Images V7** for photos that came from there (`oi_<ImageID>.jpg`): all banana, orange
  and mushroom photos and some pine cones, sunflowers and dogs. Google's box files (train split 2.26 GB) are
  streamed once and only our photos' rows are kept in `data_object/_cache/openimages_boxes.csv`.
- **OWLv2 pseudo-labels** for every other photo: OWLv2's boxes of the photo's own class (any "dog" box for the
  four breeds; the breed comes from the folder). Results are cached per photo in `data_object/_cache/`, so an
  interrupted build continues where it stopped. OWLv2 takes about 8 s per photo on this CPU and well under a second
  on a GPU, so build the full dataset on Kaggle or the GPU laptop.

Photos where neither source has a box of their class are left out: as images without boxes they would teach the
detector that the object is background. The notebook draws contact sheets (green = human, orange = OWLv2) to
spot-check the boxes. Defaults: up to 700 train and 150 test photos per class (butterfly alone has 6,500 train photos);
`val` is 10% of the chosen train photos and picks the best epoch, `test` comes from `data/<class>/test`.

Layout (YOLO format, also read by the Faster R-CNN code): `data.yaml`, `images/{train,val,test}/<class>__<name>.jpg`
(longer side at most 640 px), `labels/{train,val,test}/<class>__<name>.txt` (one `class cx cy w h` line per box,
0-1), `boxes.csv` (every box with its source and score), `info.json` (settings and counts).

### Running

Locally, open the notebooks in `object_detection_notebooks/` and run them in order (`LIMIT_PER_CLASS = 5` in 01
for a quick try; on CPU use `IMG_SIZE = 320` and a small `FRACTION` or few `EPOCHS` in 02/03).

On Kaggle (GPU and *Internet* on; the setup cell clones the **pushed** code from GitHub):

1. Notebook 01: attach the dataset made from `imgcls_data.zip` (as for the classifier notebooks), run all,
   *Save Version*. In that version's *Output*, create a new dataset from the `data_object` folder, named
   `data_object`.
2. Notebooks 02 and 03: attach the `data_object` dataset with *Add Input* and run all. For 03 to start from our
   classifier, also attach a dataset holding its run folder (`best.pth` + `summary.json`); otherwise it uses the
   ImageNet weights.

### What the two detectors are

- **YOLO** ("You Only Look Once") predicts, for every cell of a grid over the image at once, whether an object is
  centred there, its box and its class; overlapping duplicates are then removed. Ultralytics does the training
  (mosaic and colour augmentation, best epoch on val); its 80-class COCO head is replaced by one for our 10, and
  COCO's banana and orange outputs are carried over by name. Licence: AGPL-3.0, fine for learning and course work.
  `yolo26n` has 2.5M parameters and runs at about 25 ms per image on this laptop's CPU.
- **Faster R-CNN on our MobileNetV3** (`imgcls/objdet/frcnn.py`): the backbone is our classifier without its
  10-class head (timm `features_only`, strides 8/16/32, BatchNorm frozen), a feature pyramid combines its maps,
  a region proposal network suggests boxes and a box head names and refines them. The backbone already knows what
  our objects look like; the pyramid and heads learn where from `data_object/`. Training: AdamW, 1 warm-up epoch +
  cosine, AMP on CUDA, flips and mosaic (four photos in one image, so it also sees small and several objects).

Both are scored on the test split with the same code (`imgcls/objdet/metrics.py`, COCO-style): **mAP50** (a box
counts when it overlaps the true box by at least 50%) and **mAP50-95** (averaged over overlaps 50-95%, so it also
rewards tight boxes). Each run folder gets `summary.json` and `test_metrics.json` (per-class AP), example
predictions, and, with `VIDEO_PATH` set, an annotated video. `objdet.detection_runs()` lists every detection run.
Most test boxes come from OWLv2, so for those classes the test score measures agreement with OWLv2; banana,
orange and mushroom are scored against human boxes.

## How the dataset was built

### Sources

| Class | Sources |
|---|---|
| butterfly | the dataset provided at the start (already split train/test), cleaned |
| sunflower | 1,000 provided web images (many were duplicates or clip art) + Open Images V7 "Sunflower" |
| golden retriever, Labrador retriever, Siberian husky, pug | provided ImageNet/Stanford-Dogs-style images + [Tsinghua Dogs](https://cg.cs.tsinghua.edu.cn/ThuDogs/) (up to 900 per breed) + Open Images V7 breed labels |
| banana, orange, mushroom | [Open Images V7](https://storage.googleapis.com/openimages/web/index.html): bounding-box images where the object fills at least 8% of the photo, plus some verified image-level labels |
| pine cone | Open Images V7 "Conifer cone" + [Wikimedia Commons](https://commons.wikimedia.org/wiki/Category:Pinus_cones) "Category:Pinus cones" (pollen cones, seeds, drawings, fossils excluded) |

### Pipeline

1. **Collect** into a staging folder (`new_data/<class>/`, since deleted):
   - Open Images label CSVs were streamed and filtered to our label IDs with `curl ... | grep`; then
     `fetch_openimages.py` selected images (human-verified positives only, images showing two of our classes
     skipped, small/cartoon boxes skipped) and downloaded them from the Open Images S3 bucket, falling back to the
     original Flickr URLs for images without boxes.
   - `extract_thudogs.py` copied a fixed-seed sample of each breed out of the Tsinghua Dogs low-resolution archive.
   - `fetch_commons.py` walked the Commons category tree and downloaded 500px thumbnails with license/author info.
2. **Manual review:** images deleted by hand from the staging folders were treated as rejected.
3. **Screen with CLIP** (`screen_images.py`, OpenCLIP ViT-B/32 `datacomp_xl_s13b_b90k`): zero-shot probabilities
   over the 10 classes plus distractors (other dog breeds, malamute, cat, person, cooked food, lemon/lime, other
   flowers, moth, tree, text, building), and a photo/drawing/clip-art/text style score.
4. **Decide** (`apply_screening.py`; every threshold was tuned by looking at image grids of what it removes):
   - all classes: unreadable or shorter side < 96 px -> reject; drawings, clip art and packaging -> reject
     (except butterfly, whose white-background specimen photos look like clip art to CLIP)
   - dogs: reject if no dog is visible or the labelled breed gets < 10% (husky counts "malamute" as husky)
   - banana, orange: need >= 40% for their class; Open Images photos without a bounding box need >= 70%
     (the "orange" label often means the colour)
   - pine cone: needs >= 70%, and Commons photos that CLIP rates >= 90% "sculpture/ornament of a pine cone"
     are rejected (`screen_pinecone_art.py`)
   - sunflower, mushroom, butterfly: keep if the class gets >= 25%, otherwise reject only if something else is
     >= 50% confident (butterfly counts "moth" as butterfly)
5. **De-duplicate** with perceptual hashes (64-bit pHash, <= 4 bits apart = same photo; the largest copy is kept),
   **then split 70/30** with seed 42, so no photo appears in both train and test.
   Butterfly kept its original split; 2 off-topic images and 29 test images that duplicated train images were removed.

Images removed per class (screening, not counting duplicates): orange 501, sunflower 271, pine cone 300,
banana 253, golden retriever 39, Labrador 39, husky 38, pug 29, mushroom 19, butterfly 2 (+29 test duplicates).

### Lessons learned (what didn't work)

- **Open Images image-level labels without boxes are noisy**: "Orange (fruit)" included people in orange clothing,
  orange flowers and cars; "Banana" included market stalls. Fixed with stricter CLIP thresholds for unboxed images.
- **The Open Images S3 bucket only holds images that have bounding boxes**; dog-breed and pine cone images
  returned 404 and had to be fetched from the original Flickr URLs (some deleted, some rate-limited).
- **Wikimedia Commons categories contain art**: "Pinus cones" includes reliefs, coins, fountains and finials shaped
  like cones, which CLIP rates as genuine pine cones. Needed a dedicated "real vs artwork" check.
- **Commons throttles non-standard thumbnail sizes** (640px requests stalled; 500px worked).
- **The provided sunflower set had ~365 duplicate copies** (same photo, different resolution) plus clip art and
  seed packets; only ~635 unique photos.
- **CLIP calls skippers and leafwing butterflies "moths"** and white-background specimen photos "clip art"; generic
  rules would have deleted ~580 valid butterflies.
- **CLIP splits huskies between "Siberian husky" and "malamute"**; counted together.
- **CLIP ViT-B/16 was ~7x too slow on the CPU-only laptop** (~3 images/s); ViT-B/32 was used instead, at some
  cost in screening accuracy. MobileCLIP2-S2 was not faster on this CPU.
- **Automatic pruning has a bias:** it also removes hard-but-valid images (pale golden retrievers, unusual
  sunflowers), which makes our own test split somewhat easier than real-world images.
- **Training from scratch is far worse than fine-tuning.** Same architecture (MobileNetV3-Large), same data, same
  test split (5,129 images):

  | | Fine-tuned from ImageNet | From scratch |
  |---|---|---|
  | Test accuracy | 98.7% | 83.8% |
  | Test balanced accuracy | 97.8% | 79.3% |
  | Test macro F1 | 97.7% | 75.8% |
  | Epochs (best) | 10 (8) | 60 (55) |
  | Training time | 12 min, RTX 2050 | 36 min, Kaggle T4 |

  From scratch it reached 50% validation accuracy only at epoch 7 (fine-tuned: 93% after epoch 1), collapsed once
  (epochs 21-22: 74% → 53%, about 8 epochs lost) and was still underfitting when the learning rate reached zero.
  `GRAD_CLIP` was added afterwards to prevent such collapses; `resnet18_scratch` (ResNet-18, 150 epochs, clipping)
  is the stronger from-scratch attempt.

## Troubleshooting

| Problem | Fix |
|---|---|
| Setup cell prints `Using CPU` on a GPU machine | the CPU build of PyTorch is installed; reinstall from the CUDA index (see [Setup](#setup)) |
| CUDA out of memory | lower `BATCH_SIZE` (e.g. 16) or `IMG_SIZE` |
| Training is very slow | CPU-only: use `mobilenetv3_large` or `efficientnet_b0`, or `TRAIN_MODE = "linear_probe"`; lower `SAMPLES_PER_CLASS` |
| Train cell shows `Run folder: ...` and then nothing; GPU stays at idle power | image-loading workers are starting slowly or hung (Windows + CUDA PyTorch). The code now falls back to single-process loading after `LOADER_TIMEOUT` (180 s); to avoid the wait, set `NUM_WORKERS = 2` or `0` and re-run the settings, Data and Train cells |
| `WARNING: image-loading workers failed (...)` | the fallback above kicked in; training continues. Lower `NUM_WORKERS` next time |
| `/detect-video` returns `503` | install the two video packages into the venv: `pip install transformers opencv-python-headless` (both are in `requirements.txt`) |
| `/detect-video` takes minutes | expected on a CPU (about 10 s per analysed frame): lower `fps` (0.5–1) or run the API on the GPU laptop |
| Progress bar disappears at the end of an epoch | the validation bar is removed when validation finishes; the training bar stays, and the epoch summary line follows |
| `WARNING: no training images yet for [...]` | a class folder is missing from `data/`; the model will have fewer outputs |

## Known limitations

- **Orange (574 images) and pine cone (695) are the smallest classes.**
- **The cleaning was automatic** (CLIP), spot-checked with image grids but not reviewed image by image; a few
  wrong images remain (e.g. orange-coloured objects, jam jars among pine cones).
- **The model always answers with one of the 10 classes**, even for unrelated images.
- **The staging folders were deleted**, so `data/` cannot be rebuilt from the sources without re-downloading.
  The download scripts and manifests document how it was built; the provided butterfly, sunflower and original dog
  images are not re-downloadable by the scripts.
